# 手順4：VHを使用しない追加評価

ここは2026-09-06に新しく作成・実行した静的評価の成果物である。`result/` と `Paper/analysis/` の過去証拠を上書きしない。入口は [Report.md](Report.md)、詳細設定は [config.json](config.json)、実行状況は [completion.json](completion.json)。TeX/LaTeX、VH、Notebook全体は実行しない。

### 前提条件ラベル

ラベルはLLMではなく `scripts/nonvh_analysis.py:evaluate` で決定する。これは `precondition.json` の8操作・16原子条件の手動転記であり、単一条件反転テストを行う。条件辞書そのものの正当性を検証したことにはならない。合成構造化事実 `facts` は既知の有限集合としてclose/heldを表現し、集合にないものを非該当とする。状態の未指定はunknown（情報不足）とし、falseと混同しない。falseが1つあれば連言はfalse、不明だけ残ればunknown。空のclose/heldは旧変換関数では文として表示されないので、モデルにはこの閉世界仮定が明示されていない。この表現上の曖昧さも含む限定的な検査である。

環境文字列は公開Notebookから抽出した `Paper/listings/knowledge_serialization.py` で生成する。合成物体IDは101～104、部屋900。全グラフの知識抽出処理は実行しない。前提条件判定のメッセージ配列は照合済み `prompt_spec.py` を再利用し、正解ラベル・違反条件は判定API入力へ含めない。unknownは二値精度の分母から除外し、生応答を残す。状態が不明なPUTINをCLOSEDでないと断定しない保守的評価器であり、過去実装をこれに置き換えてはいない。

元実装に合わせ、Yesが含まれる応答を受理とする。完全なYes/Noに一致するかも別列へ保存する。物体名・ID・引数数・書式の検査は新しい採点器の診断であり、元の `bind_conditions` と同じバリデータではない。

### 終了判定ラベル

状態変化はJSON挿入順で、各タスク名について初期ゴール充足/不充足が初めて現れる各1例を選ぶ。初期状態配列とゴール状態配列のID別一致を独立ラベルにする。ゴールJSONをAPIに渡さず、初期状態とタスクだけから新しい状態専用テキストを作る。部屋・距離・保持・その他オブジェクトは回収できないため追加しない。これは歴史的な `return_nlp` 出力ではなく、制御された新しい表現である。

配置は2個のappleとfridgeの合成例。両方INSIDE、片方ON、両方ON、両方INSIDEかつfridge CLOSEDの4例。閉扉自体はこのタスクのゴールではない。非ゴール制約を勝手に追加していないかを見る最小例である。End完全一致を終了分岐として採点し、Continue以外の非End出力は別途非定型応答として数える。ゼロ長参照による元実装の成功特例は適用せず、終了コンポーネント単体を測る。

### A-2の部分比較

これは事前に固定した不正候補を使った修正コンポーネントの小規模比較であり、計画全体のA-2条件の実装・完了ではない。

- C0：候補をそのまま採用するオフライン対照。行動生成APIは呼ばない。
- C1：既存のLLM判定→必要時の違反特定→1回再生成。判定のrepeat=0を再利用する。Yes受理なら無修正。
- C2：同じ合成構造化事実に対する記号判定→違反条件を既存feedback文に埋めて同じLLMで1回再生成。検証器に追加のグラフ情報は与えない。
- C4：具体的な違反条件を与えず、同じ生成器に再考を求めて1回再生成。再生成回数と上限だけ一致し、総呼び出し数・入力文面・総トークンは一致しない。「同予算での効果」とは主張しない。

Multiプロンプト、事例空文字、履歴空、固定候補を使う。タスクは `run_nonvh_api.py` に固定する。再生成後のJSON条件評価は分析のためにのみ行い、再生成ループへ戻さない。条件を満たすWALK等を出しても、タスクを前進させたとは限らない。厳密書式と前後空白除去後のラベルを別記する。違反説明の意味的正しさは [unmet_review_blank.csv](unmet_review_blank.csv) に正解条件と応答を並べ、人手採点は空欄のままとする。

### 検索比較

候補集合は種別ごとの既存exampleタスク名。semanticは凍結済みMiniLMスコア行列を再使用。fixedは辞書順で最初の名前。randomは名前を一様抽出し、基準seed 20260906・種別・ID・反復からSHA-256で入力単位の乱数を固定する。選択名内で最長参照列、長さ同値なら元JSONの先頭を使用する。この規則は全条件共通。noneは事例なし。random3反復、他は決定的1回で合計2,490選択行。元Notebookの集合列挙順による同点処理は復元できないが、保存スコア上のsemantic最大値に同点はなかった。

全て事例選択に関する**記述統計**であり、他条件の選択結果に過去semanticの成功率を流用しない。対象・操作・配置先の一致は文字列からの構造特徴で、人手適合ラベルではない。状態変化には配置先がないため一致率を空欄にする。

### 著者確認によるケース説明への計画変更

[human_case_selection_author_only.csv](human_case_selection_author_only.csv) は旧案の24候補であり、参照列長、対象数、シーン、IDで昇順に並べた12等間隔順位点を種別ごとに選んだ。成否ラベルを選択に使わず、全シーン・難易度要因を均等に割付けた設計でもない。ユーザーの指示により、現在の計画は[Update-Plan.mdのB-4-2](../Update-Plan.md#b-4-2著者による代表タスクの確認と難易度の説明)に記載した、著者による少数ケースの確認・説明へ変更した。24候補は参考資料として保持し、全件確認や被験者実験は必須としない。

状態変化・配置から各2～3件、計4～6件を目安に、著者が初期条件・ゴール・参照解・既存結果を確認し、必要な判断、操作手順、難しい点、根拠と限界を説明する。著者名・確認日・未確認事項を記録し、説明案を自動生成しただけで著者確認済みとは扱わない。VHなしで確認できる範囲を明示し、実行可能性や最短性は保証しない。人間の成功率・所要時間は測定せず、人間ベースラインとは呼ばない。

この作者用表には参照解・ゴールが含まれ、新方針の著者確認では閲覧してよい。将来別途被験者実験を行う場合にはそのまま被験者へ渡さない。`human_labels_blank.csv` は旧案の空の記録票として保存し、新方針で埋める必要はない。APIのLLM応答を人間ラベルとして扱わない。著者確認自体は未実施であり、今回の変更は計画のみである。

## 再実行

オフライン再生成（同一コードなら決定的。既存のapi_logは変更しない）：

```bash
python3 scripts/nonvh_analysis.py
python3 -m unittest discover -s scripts -p test_nonvh.py -v
python3 scripts/summarize_nonvh.py
python3 scripts/verify_nonvh.py
```

APIは利用者の許可とネットワークアクセスが必要：

```bash
python3 scripts/run_nonvh_api.py --execute --limit 2
python3 scripts/run_nonvh_api.py --execute --limit 400
python3 scripts/summarize_nonvh.py
```

Python標準ライブラリのHTTPS経由で公式Chat Completionsエンドポイントだけを呼ぶ。キーは利用許可済みのルート `.env.local` の `OPENAI_API_KEY` をメモリで読み、シェルとして実行しない。ファイルはgitignore対象。生ログにヘッダ・キー・env全体を保存しない。モデル・入力一致を検査して成功要求を再利用し、失敗時は自動リトライせず停止する。limitはその起動での新規要求数。費用上限は全ログ累積で2米ドル。要求前の入力UTF-8バイト数＋余裕分と最大出力160tokensから保守的に予約し、成功時usageで計上する。失敗時は予約額を上限判定に残す（実請求ではない）。HTTP送信成功後ログ保存前にプロセスが失われた場合の二重送信・課金は完全には排除できない。

API仕様の確認には[公式Chat Completionsリファレンス](https://developers.openai.com/api/reference/python/resources/chat/subresources/completions/methods/create)を利用した。新しいmax_completion_tokens=160とログ収集を導入し、当時の未回収設定と区別する。公式価格に基づく推定は請求額の保証ではない。
